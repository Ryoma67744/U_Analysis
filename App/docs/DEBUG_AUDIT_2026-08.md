### 判定

すべての指摘は、それを見つけた監査担当とは**別の検証官**が「この主張は間違っている」と示すことを目標に再検証した（反証審査）。その結果を次の 3 つに分けている。

- **確定**（UPHELD）：反証を試みたが崩せなかった。
- **条件付き**（WEAKENED）：機構は正しいが、影響範囲や重大度が過大だったので訂正した。
- **誤検出**（OVERTURNED）：反証が成立した。**隠さず §4.4 / §5.5 に公開する**（監査が「疑いをすべて事実にしていない」ことの証明として残す）。

### 修正区分

- **機械的修正**：直しても解析結果の数値は変わらない。設計判断も不要。
- **要科学的判断**：直すと**過去の解析結果と数値が変わる**。研究上の判断が必要。
- **要設計判断**：仕様をどうするかの選択が必要。

### 結論を一言で

**アプリは「落ちない」。しかし「黙って言うことを聞かない」箇所が多数ある。**

### ②「ボタンが違う動作をする／反映されない」の原因の総括

過去に体験された症状は、次の 4 つの型に整理できた。いずれも**エラーを出さずに失敗する**共通点がある。

1. **「変更しない」を返してしまう型**（最多）— 内部で「値が無ければ画面を更新しない」という書き方をしているため、**前の値が residual として残る**。サブプロジェクト切替のフォルダ残留（#7）、プリセット読込が効かない、が該当。
2. **後から自動処理が上書きする型** — 利用者の操作で正しい値が入った直後に、別の自動切替処理が既定値で塗り潰す。プリセットの付加イオン設定・再解析のイオンモードなどが該当。
3. **画面と計算で別の値を見る型** — 表示名で照合すべきところを内部 ID で比べている等。クラスタ名を変えると統計表示が「0 pixels」になる、が該当。
4. **宣言した相手が存在しない型** — 削除済みの画面部品に書き込もうとして、その処理全体が停止する。解析者名が空欄（#6）が該当し、**過去にも同型で「参照」ボタン 35 個が一斉に無反応**になった事故がある。

## 2. 調査方法

### 2.1 「読んだ」だけで終わらせない

コード読解だけでは、このアプリで過去に起きた不具合（宣言はあるが実体がない、修正したつもりが空振り）は捕まえられない。そこで**実際に動かす**ことを軸に据えた。

1. **アプリを 2 通りで起動**：認証設定を与えない場合（①-1 の再現）と、正しく与えた場合（探査用）。
2. **稼働中のアプリから「登録済みコールバック一覧」を採取**（381 件）。以後すべての静的解析はこの実データと突合し、「コードには書いてあるが実際には登録されていない」を検出できるようにした。
3. **実ブラウザ（Chromium）で操作**：ログイン → 全ページ巡回 → タブ切替 → 見出しの開閉 → ボタン押下、を自動実行し、ブラウザ側のエラー・サーバ応答を全件記録。
4. **疑わしい挙動は最小再現アプリを書いて実測**：例えば「削除ボタンの二重処理」疑惑は、同じ構造の小さなアプリを作り実ブラウザで 5 回試行して**誤検出と判明**した（§4.4）。
5. **統計の主張は数値で例証**：BH 補正・Otsu 閾値・平滑化の近傍探索などを numpy／base R で再現し、影響の大きさを数値で示した。

### 2.2 多段の分業と「反証させる」体制

- **第 1 段（発見）**：27 の担当に分けて全数監査。コールバックはモジュール別 11 群＋多重書込み＋ブラウザ側、R は現用 17 本＋統計手法＋設定の受け渡し経路。
- **第 2 段（反証）**：第 1 段の指摘を**別の検証官**に渡し、「間違いだと示せ」と指示。他所のガード・後段での上書き・到達しない分岐・既定値・ライブラリの実挙動を探させ、崩せなかったものだけを「確定」とした。
- 結果、**誤検出 1 件を摘出**（§4.4）、**重大度の過大評価 15 件を格下げ**した。**この報告書に載る「確定」は、いずれも一度は反証を試みて生き残ったものである。**

### 2.3 環境と再現性

- 元リポジトリは**一切変更せず**、複製に対して実行した（アプリが実行時にリポジトリ内へ書き込む設計のため）。
- Python 3.11／dash 2.18.2／R 4.3.3（base のみ）。**Seurat は導入していない**ため、R 解析の実行そのものは行っていない（§8 の制約）。

## 3. ① アプリ実行時のエラー

### 3.1 総括：サーバ側は健全

| 確認項目 | 結果 |
|---|---|
| HTTP 4xx / 5xx | **0 件** |
| コールバックのエラー応答 | **0 件** |
| 未捕捉の例外（page error） | **0 件** |
| 起動シーケンス | 正常（コールバック 381 件を登録、`/healthz` 緑） |
| R スクリプトの構文 | 現用 17 本・死蔵 34 本すべて OK |
| 既存テスト | 1,756 件すべて緑 ＋ E2E 19 件緑 |

**「アプリ実行時にエラーがないか」への回答は「サーバ側にエラーはない」である。** ただし以下 3 点は実行時の問題として確定した。

### 3.2 [S1・実行確認] Docker を使わない起動では、認証設定の保存先が固定パスで壊れる

認証情報の保存先が `/app/Data/Other/common/auth.json` という **Docker コンテナ内にしか存在しない住所**で決め打ちされている（`App/app/services/auth_service.py:25-33`）。環境変数 `AUTH_CONFIG_PATH` で上書きできるが、この変数は `.env.example`・`setup.sh`・`setup.bat`・`SETUP_GUIDE.html`・`DEPLOY.md` の**どこにも書かれていない**。

実測した挙動：

- **管理者権限で起動した場合**：ファイルシステムの最上位に `/app/` を勝手に作り、そこにパスワードのハッシュを書き込んだ（アプリは起動する）。意図しない場所に認証情報が残る。
- **一般ユーザー権限で起動した場合**：`PermissionError: '/app'` で**起動できない**。

さらに副次的な問題が 2 つある。(a) ファイルの親フォルダを作る前にロックを取ろうとする順序になっている（現行のロックライブラリが親フォルダを作るため今は表面化しない）。(b) `config.py:64` は `Data/Other/Common`（大文字 C）を使うのに認証は `common`（小文字）を使う。大文字小文字を区別する環境では別フォルダになり、`.gitignore` も小文字側を除外していないため、生成された認証ファイルが誤ってバージョン管理に入りうる。

**波及**：自動ブラウザテスト（E2E）の起動処理も同じ経路を通るため、この環境変数を与えないと E2E は「失敗」ではなく**「依存不足の可能性」として黙ってスキップ**される。つまり**テストが動いていないことに誰も気づけない**状態だった（正しく与えたところ 19 件すべて緑になった）。

### 3.3 [S2・実行確認] ログインしても解析者名が常に空欄

ヘッダーの「解析者: ○○ (tier)」を表示する処理が、**ver52.3 で画面から削除された部品**（`header_analyst_label_shared`）に書き込もうとしている（`App/app/callbacks/auth_callbacks.py:52-55`）。

実ブラウザでの実測：

```
header_analyst_label_landing  : 存在する / 中身は空文字 ""
header_analyst_label_analysis : 存在する / 中身は空文字 ""
header_analyst_label_shared   : 存在しない
コンソール: ReferenceError: A nonexistent object was used in an `Output` of a Dash callback.
            The id of this object is `header_analyst_label_shared` ...（ページ遷移のたびに発生）
```

存在しない 1 か所のせいで**処理全体が実行されず、実在する 2 か所にも名前が入らない**。裏側では解析者情報が正しく用意されているのに、表示段で止まっている。共有サーバで複数人が使う場合、**別人のアカウントのまま作業していても気づけない**。

これは「宣言した相手が存在しない → 例外も出ず機能だけが消える」という、このリポジトリで繰り返し起きている型である（同型で「参照」ボタン 35 個が一斉に無反応になった事故が ver42.1 にある）。**現在この型を検出するテストは存在しない。**

### 3.4 [S4・実行確認] もう 1 か所、同種の「存在しない部品」がある

`fs_umap_exclude_cluster` も同じエラーを出し続けている（`interactive_fullscreen.py:140` で全画面モーダルを開いたときだけ作られる部品を、常時参照している）。ただしこちらはモーダルを開けば実在するため、実害は「コンソールが恒常的にエラーで汚れ、本物のエラーが埋もれる」ことに留まる（§3.3 とは重大度が異なる）。

### 3.5 [S3・コード確認] 解析の起動に失敗すると「実行中」表示が残り続ける

解析開始時、記録簿に「実行中」と書いてから R を起動する（`analysis_runner.py:1029` → `:1102`）。R の起動自体に失敗した場合、記録簿を書き直す処理がないため、実際には何も動いていないのに「実行中」の表示が残る。次回アプリ再起動時の整合処理で解消されるが、それまでは誤った表示が続く。

### 3.6 [S3] 科学的に正しい統計機能が UI から呼び出せない

サンプル単位の検定（pseudobulk）、空間統計（Moran's I）、クラスタリング安定性評価が実装され、テストも通っているのに、**どの画面からも呼び出す経路がない**。しかも画面の注意書きは「群間の主張にはサンプル/ROI 集約（pseudobulk）をご利用ください」と**利用者に案内している**（`caveats.py:24`）。案内された機能が存在しない状態になっている。

## 4. ② ボタン・UI の結線

### 4.1 まず「良い知らせ」：ボタンの取り違えは 1 件もなかった

**214 個すべてのボタンについて、押下を受け取る処理が実在することを機械照合で確認した（未結線ゼロ）。** 「A を押したのに B の処理が呼ばれる」という配線間違いも、ボタン ID の取り違えや紛らわしい重複も**発見されなかった**。全ページが最初から描画される設計のため、「画面にない部品を指す」種類の事故も起きにくい。

したがって、ご経験された「押しても別のものが実行される」は、**配線が入れ替わっているのではなく、正しく呼ばれた処理が途中で黙って諦めている**か、**直後に別の処理が結果を塗り潰している**ために、そう見えていたと考えられる。以下がその実体である。

全 214 ボタンの対応表は**付録A**、全 353 コールバックの監査結果は**付録B**、各指摘の詳細（症状・根拠・再現手順・修正方針）は**付録C** にある。

### 4.2 型別に見た原因

#### 型 1：「変更しない」を返すため、前の値が残る

**［S2・実行確認］サブプロジェクトを切り替えてもフォルダが前のまま**（`project_callbacks.py:692`）

サブプロジェクト B の「解析」を押すと、B に保存された設定がない項目については「画面を変更しない」という指示が返る。その結果、直前に開いていた A のデータフォルダ・出力先が**そのまま残る**。画面のどこにも「今どのサブプロジェクトを操作中か」の表示がないため、気づく手段がない。そのまま実行すると **A のデータを解析し、A の出力先に書き、記録上は B の解析**になる。

同じ問題は ver52.3 に「インタラクティブ解析」側で修正済みで、コードにその旨のコメントまで残っている。**解析設定側にだけ同じ修正が適用されていない。**

実測（実ブラウザ）：A を開いた後に B を開くと、サーバ応答にフォルダ欄が含まれず（＝変更しない）、画面は A のパスのまま。

**［S2・実行確認］閾値に 0 を入れると既定値に化ける**（`analysis_callbacks.py:527`）

「log2FC 閾値」に **0**（＝倍率で絞り込まない、という正当な指定）を入れて実行すると、実際の計算には 0.25 が使われる。プログラム上「0 は値が無いのと同じ」と扱う書き方をしているため。画面は 0 のままなので、指定どおり解析されたと信じてしまう。同じ入力欄でも**再解析側は 0 を正しく通す**ため、経路によって解釈が違う。

#### 型 2：直後に自動処理が上書きする

**［S2・実行確認］プリセットを読み込んでも一部の設定が既定値に戻る**（`file_handlers.py:505` 他）

プリセットを読むと「✅ 読み込みました」と出るのに、**付加イオン（Adduct）フィルタだけは保存した組み合わせにならない**。プリセット読込が「イオンモード」を書き換えた瞬間、それに連動する自動切替処理が発火して既定の組み合わせで塗り潰すため。同型の上書きが「再解析のイオンモード・m/z 許容誤差」「サブプロジェクトのデータフォルダ」でも起きる。

**［S2・実行確認］キャリブレーションのプリセットが対応表に反映されない**（`analysis_callbacks.py:2110`）

プリセットを選ぶと成功メッセージは出るが、リファレンス/実測値の対応表がまったく変わらない（空のまま、または直前の内容のまま）。**プリセット保存機能が事実上使えない状態。**

#### 型 3：画面と計算で別の値を見る

**［S2・実行確認］クラスタに名前を付けると統計が「0 pixels」になる**（`interactive_cluster.py:99`）

クラスタを「Tumor」などに改名した後、クラスタ統計の表で行を選ぶと、右側の説明が「Tumor: 0 pixels (0.0%)」になる。表示名で照合すべきところを**内部のクラスタ番号と突き合わせている**ため、必ず一致しない。同じ画面の表には「100 pixels / 33.3%」と正しい数字が出るので、どちらが本当か分からなくなる。

#### 型 4：宣言した相手が存在しない

§3.3 の解析者ラベルが該当（詳細は §3.3）。

### 4.3 「変更が反映されない」の核心：見出しを畳むと図が古いまま

**［S2・実行確認］**（`interactive_umap.py:534`／`interactive_spatial.py:1114`）

UMAP や Spatial の見出し（アコーディオン）を**畳んだ状態**でクラスタ名の変更・色の変更・マージ表示の切替などを行い、そのあと見出しを開き直しても、**図が変更前のまま表示される**。設定欄は新しい値なのに図だけが古い、という食い違いが起きる。そのまま「一括保存」や PowerPoint 出力を行うと、**古い図が成果物として保存される**。

重要なのは、**この問題は ver51.9 で一度「修正済み」とされている**点である。今回の検証で、その修正は**挙動を何も変えていない空振り**だったことが判明した（見出しが閉じている間は状態が記録されないため、開き直したときに「変化なし」と誤判定される）。加えて UMAP 側では利用者ごとの識別が付いておらず、**複数人が同じ結果を開くと互いの状態を上書きし合う**。

### 4.4 疑ったが「白」だった項目（誤検出の公開）

監査が「疑いをすべて事実にしていない」ことを示すため、反証が成立した項目も記録する。

1. **削除ボタンの二重処理疑惑 → 白**。「削除確認を押すと 2 つの処理が同時に走り、片方が対象を消してしまうので削除が効かないことがある」と疑ったが、**同じ構造の最小アプリを作り実ブラウザで 5 回試行したところ、5 回とも正常に削除された**。Dash は片方が消す前の値をもう片方に渡す仕様のため、順序に関係なく成功する。ただしこれはライブラリの実装詳細に依存しており、将来の更新で崩れうる構造ではある（S4 の設計メモとして記録）。
2. **マーカー表の絞り込みが古い値のまま残る疑い → 白**（`interactive_loupe.py:359`）。ドロップダウン部品自身が「選択肢に無い値を自動で空に戻す」実装を持っており、実測でも残らなかった。
3. **解析者ラベル問題の「影響は軽微」という評価 → 誤り**。当初「本番では無症状」と評価した検証があったが、実ブラウザで**全ユーザーに常時見える形で機能が失われている**ことを確認し、評価を覆した（§3.3 が正しい）。

### 5.2 【最重要】解析結果が実際に誤る問題（S1・5 件）

#### 5.2.1 キャリブレーションで「使わない」に外した点が補正計算に混ざる ［実行確認］

`App/app/services/analysis_runner.py:278`

除外の判定が「値が空かどうか」で書かれているが、実際に入る値は文字列の `"Yes"` / `"No"` である。プログラム上 **`"No"` という文字列は「空ではない」＝「使う」と判定される**ため、チェックを外した行も回帰計算に入る。

実測（4 点のうち 1 点を「使わない」にした表を渡した）：

| | 使用点数 | m/z 400 での補正量 |
|---|---|---|
| 現状（誤） | 4 点（除外されない） | **+0.04337 Da** |
| 正しい挙動 | 3 点 | +0.00120 Da |

差 **0.042 Da** は、化合物照合の既定許容値 0.01 Da の **4 倍**にあたる。

さらに悪いことに、実行時のサマリー表示は `"Yes"` の行だけを「使用ピーク」として出すため、**画面には出ていない点が計算に入っている**という、目視で気づけない構造になっている。補正係数は R 側で全特徴量の m/z 名を書き換え、名前が衝突した特徴量は統合されるため、影響は化合物名の間違いに留まらず**発現行列そのものの変質**に及びうる。

なお、**対話画面（インタラクティブ解析）側の同じ処理は正しく実装されている**（`interactive_calibration.py:1197`）。つまり「対話画面で妥当性を確認してから本解析」という運用をしていた場合、**確認した補正曲線と実際に適用された補正曲線が別物**になる。

→ 過去に「使わない」行を含む表でキャリブレーションを行った解析は、**係数の再検証が必要**。

#### 5.2.2 クラスタを選んで再解析すると、選んだスポットの約半分が消える ［実行確認］

`App/Script/DESI/DESI_RDS_ClusterFilter_ver3.R:275`

再解析は本解析スクリプトのコピーを**文章として書き換えて**実行する仕組みで、そのうち「背景除去はもう済んでいるので飛ばせ」という書き換え指示が、本解析側の記述変更に追従できず**空振り**している。結果、**すでに背景除去済みのデータにもう一度自動しきい値処理（Otsu 法）がかかる**。

Otsu 法は「与えられたデータを 2 グループに分ける閾値」を毎回計算し直すため、既にフィルタ済みのデータに再適用すると、**残った中でさらに信号の弱い側が切り捨てられる**。信号強度の低い組織（脂肪、壊死部など）は選択的に失われる。画面にもログにも警告は出ない。

#### 5.2.3 DESI の複数サンプル（RPCA）だけ、補正後の値でマーカー検定している ［実行確認］

`App/Script/DESI/260623_DESI-UMAP_Template_v16.R:2805, 2930`

サンプル間の位置合わせ用に加工した値（integrated アッセイ）を元に戻さないまま差次発現検定を実行している。Seurat の公式見解でも、統合後の補正値での検定は推奨されない（値が再構成されたもので、負値も取りうるため）。

### 5.4 クラスタ統合（マージ）機能が成立していない ［実行確認］

「クラスタを絞り込んで再解析し、その結果を元の UMAP に貼り戻す」機能について、**DESI・TIMS の両方で、別々の担当が独立に「構造的に成立しない」と結論した**。

- **DESI**：再解析で書き出すファイル名に `_KEEP_Cl_8` のような接尾辞が付くため、元データ側のピクセル名（`sample|101`）と再解析側（`sample_KEEP_Cl_8|101`）が**一致しない**。統合は最後の一歩で必ず失敗し、**解析全体が赤いエラーで終了**する（UMAP もクラスタも DEG も計算し終えた後に）。エラー扱いになるため結果フォルダがプロジェクトに自動登録されず、画面のプルダウンにも出てこない。
- **TIMS**：同じ接尾辞問題に加え、内部でピクセルの照合キーが**すべて NA（欠損）になる**書き方の誤りがある。こちらはエラーを出さずに完走し、ログには「保存しました」と出るが、**中身は何も貼り戻されていない**。

つまり **DESI は「必ず失敗する」、TIMS は「成功したように見えて何もしない」**。どちらも利用者は正しい結果を得られない。

### 5.5 統計手法そのものの評価

数値例証を伴って検証した結果、以下は**手法の選択として議論の余地がある**もので、バグではない。ただし現状の挙動が利用者の期待と食い違う点は指摘しておく。

- **多重検定補正（BH法）の対象範囲**：検定前に足切りされた特徴量が補正の分母に入らないため、補正後 p 値が本来より小さく（有意になりやすく）出る。加えて**既定の p 値閾値 0.05 のままだと、CSV に出る特徴量はすべて「有意」判定になる**ため、この設定は実質的に効いていない。
- **空間平滑化の効き方がデータ依存**：探索半径が座標の単位に対して固定値（0.1）のため、座標がピクセル番号や µm だと**平滑化は何もしない**（それでも記録上は「平滑化済み」になる）。0.05 mm 刻みなら 10〜12 近傍を平均する強い平滑化になる。**同じ設定でもデータセットによって前処理が別物**になる。
- **ピクセル＝独立標本の扱い**：現在の p 値はすべてピクセルを独立標本として計算している。コード自身は「探索的な順位付けであり群間推論ではない」と正直にラベル付けしており、正しい代替（サンプル単位の検定）も実装済みだが、**UI から呼び出せない**（§3.6）。

指摘を「直しても過去の結果が変わらないもの」と「変わるもの」に厳密に分けた。**§7.1 のみ本調査の承認範囲（明白なバグ修正）に該当する。**

### 7.1 Tier 1：数値が変わらない機械的修正（34 件・実施を推奨）

これらは**修正しても過去の解析結果の数値は 1 つも変わらない**。UI の動作が仕様どおりになるだけである。各修正には「そのバグを検出する失敗テスト」を先に追加し、再発を防ぐ。

主なもの：

| 項目 | 内容 |
|---|---|
| 認証設定パスの可搬化（§3.2） | 環境に応じて決まる方式へ。大文字小文字の統一、フォルダ作成順の是正 |
| 解析者ラベルの復旧（§3.3） | 存在しない書き込み先を削除するだけ。**併せて、この型を検出するテストをブラウザ側処理にも拡張**（見逃しの穴を塞ぐ） |
| サブプロジェクトの設定残留（§4.2） | ver52.3 で別画面に適用済みの修正を、解析設定側にも適用 |

| RDS 軽量化の進捗バーが 0% 固定 | 進捗の読み取り指定の誤りを是正 |
| 共有リンクが最新結果を指す | 共有時の結果フォルダを固定する |
| 解析起動失敗時の「実行中」固着（§3.5） | 失敗時に記録を書き直す |
| Methods モーダルの再施錠 | 閉じたら施錠状態へ戻す |

### 7.2 Tier 2-A：明白なバグだが、直すと結果の数値が変わる（承認待ち・強く推奨）

**動作が仕様と違うことは確定している**が、修正すると過去の解析と数値が変わるため、研究上の判断としてご承認をいただきたい。

### 7.3 Tier 2-B：科学的な方針判断が必要（選択肢の提示のみ）

- **多重検定補正の対象範囲**（検定した全特徴量で補正するか、現状のまま足切り後で補正するか）
- **空間平滑化の扱い**（半径を座標単位に依らない指定にする／UI から設定可能にする／既定を無効にする）
- **「補正なし」シナリオの定義**（ファイル単位の Harmony を止めるか、Methods 文の記載を実処理に合わせるか）

- **p 値ゼロの人工値が CSV に混入する件**（図用と出力用を分けるか）

## 8. 本調査の制約

1. **R 解析の実行そのものは行っていない**。Seurat を含む R 解析環境の構築は本調査の範囲を超えるため、③の検証は「コードの精読 ＋ 数式・アルゴリズムの数値例証（numpy／base R）＋ 設定受け渡し経路の実測」で行った。**実データを流した結果の比較はしていない**。
2. **実データを搭載していない**。ログイン・画面遷移・ボタン押下・設定の受け渡しは実測できたが、「実際の MSI データを読み込んだ後の挙動」は検証できていない。§5 の各項目のうち、影響の**大きさ**（例：何割のスポットが失われるか）は実データでの確認が望ましい。
3. **重大度は運用実態に依存する**。例えば §5.2.1 は「キャリブレーション表で点を外す運用をしていたか」で影響が変わる。
4. **S3・S4 の一部（12 件）は反証審査が未完了**（重大度中以下の項目のみ。S1・S2 はすべて審査済み）。
